# Recommended A2 technical stack

I checked current model/tool availability rather than relying only on the versions present in the template.

The current PaddleOCR line has a particularly relevant development: **PaddleOCR-VL 1.6**, released May 28, 2026, with improved recognition of text, formulas, tables and charts, and using PP-DocLayoutV3 for layout analysis. Its documented architecture explicitly separates layout analysis from element recognition. ([GitHub][1])

However, the course scaffold specifically asks you to implement separate `layout.py` and `ocr.py`, and its mandated software stack is primarily PyTorch/Hugging Face. So I would **not blindly replace the architecture with PaddleOCR-VL**.

Instead, I recommend this A2 stack:

| Stage                     | Recommended choice                                                                                                      | Reason                                                                               |
| ------------------------- | ----------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| Ingest                    | Pillow + filesystem traversal                                                                                           | Minimal, deterministic                                                               |
| Preprocess                | OpenCV/Pillow classical processing                                                                                      | Reproducible and cheap                                                               |
| Layout                    | **PP-DocLayoutV3 / PaddleOCR layout component**, wrapped behind your `layout.detect()` interface                        | Strong current document-layout model                                                 |
| OCR                       | **PaddleOCR-VL 1.6 as a benchmark/reference**, plus a Hugging Face OCR model for the required reproduced/adapted method | Lets you satisfy the course's reproduction requirement without ignoring current SOTA |
| OCR reproduction baseline | `microsoft/trocr-base-printed`                                                                                          | Explicitly intended as a pretrained OCR foundation and naturally fits the scaffold   |
| Chunking                  | paragraph/region-aware chunks, ~256 tokens with overlap                                                                 | Preserves page/region grounding                                                      |
| Embedding                 | **BAAI BGE-M3** if multilingual/notation retrieval matters; smaller SentenceTransformer model if resource constrained   | Strong general retrieval representation; standard SentenceTransformers API           |
| Vector index              | **FAISS HNSW**                                                                                                          | Already specified by the template and inexpensive                                    |
| Retrieval                 | dense cosine/IP retrieval                                                                                               | Clean baseline for A2                                                                |
| Reranking                 | defer to A3                                                                                                             | Retrieval/reranking becomes part of the agent/evaluation milestone                   |
| Experiment tracking       | W&B as mandated by course                                                                                               | Matches handbook stack                                                               |
| Runtime                   | PyTorch + Lightning + Hugging Face                                                                                      | Matches the course substrate                                                         |

BGE-M3 is currently available through SentenceTransformers and exposes a 1024-dimensional embedding representation; its current model artifact is substantially larger than MiniLM, so whether we use it will depend on your compute budget. ([Hugging Face][2])

For OCR, TrOCR is still a legitimate pretrained foundation: its model is an image encoder + autoregressive text decoder and is explicitly intended for OCR on single text-line images. ([Hugging Face][3])

The important distinction is:

**current best model ≠ automatically best choice for this assignment.**

We need a model that is simultaneously current, compatible with the locked interfaces, trainable on your hardware, reproducible, and defensible in the A2 form.

Agent: Black and Ruff are both **Python code-quality tools**, but they solve different problems.

The simplest way to think about them is:

> **Black decides how your Python code should look.**
> **Ruff checks whether your Python code has common problems — and can also format it.**

# 1. Black: the automatic Python formatter

**Black is a code formatter.**

Its job is to take Python code written in many different styles and transform it into one consistent style.

Suppose you write:

```python
def calculate_area(radius):
    if radius>0:
        return 3.14159*radius**2
    else:
        return 0
```

Black would reformat it into something like:

```python
def calculate_area(radius):
    if radius > 0:
        return 3.14159 * radius**2
    else:
        return 0
```

The important point is:

**Black is primarily concerned with presentation, not whether your program is logically correct.**

For example:

```python
x = 10
unused_variable = 20
print(x)
```

Black doesn't care that `unused_variable` is unused.

As long as the syntax is valid Python, formatting is its job.

# 2. What exactly does Black change?

Black makes decisions about things such as:

### Indentation

Instead of:

```python
def foo():
 print("hello")
```

you get:

```python
def foo():
    print("hello")
```

### Spaces

Instead of:

```python
x=1+2
```

you get:

```python
x = 1 + 2
```

### Line wrapping

Suppose you have:

```python
result = some_function(first_argument, second_argument, third_argument, fourth_argument, fifth_argument)
```

Black may turn that into:

```python
result = some_function(
    first_argument,
    second_argument,
    third_argument,
    fourth_argument,
    fifth_argument,
)
```

This makes formatting consistent across the project.

### Quotes and strings

Black has a standard style for string quoting and related syntax.

### Blank lines

It standardizes spacing between functions, classes, imports, and blocks.

# 3. Why is Black useful in a team?

Imagine three teammates write Python.

Person A likes:

```python

    data = open(path)
    return data
```

Person B likes:

Person C likes:

```python
def load_data(
    path
):
    data = open(
        path

    return data
```

All three might represent the same basic logic, but the repository becomes visually inconsistent.

Black gives everyone one shared formatting standard.

That has a practical benefit for Git:

```text
without formatter

→ noisy diffs
→ harder code review
```

versus:

```text
with formatter

→ smaller meaningful diffs
```

Black explicitly aims for consistency, generality and readability while reducing unnecessary Git diffs. Ruff's formatter follows essentially the same philosophy. ([Astral Docs][1])

# 5. Ruff: the much broader tool

Ruff is fundamentally a **Python linter**, although it now also has a formatter. It is written in Rust and is designed to be extremely fast. The current Ruff documentation describes it as a linter and formatter with over 900 built-in lint rules. ([Astral Docs][2])

The main command is:

```bash
ruff check
```

This examines your Python code for problems.

For example:

```python
import os
import numpy as np

x = 10
print(x)
```

If `os` isn't used, Ruff can report the unused import.

Depending on the enabled rules, Ruff can identify things such as:

* unused imports
* unused variables
* undefined names
* questionable Python constructs
* deprecated syntax
* imports that should be reorganized
* many common bug patterns
* code-quality/style issues

Ruff has reimplementations of rules associated with tools such as Flake8, isort, pyupgrade, autoflake, and others. ([Astral Docs][3])

# 6. Ruff can actually fix some problems

This is one of the reasons Ruff has become so popular.

You can run:

```bash
ruff check --fix
```

For example, imagine:


Ruff can recognize that `os` isn't used and remove that import.

```text

   ↓
automatically fix safe problems
```

# 16. One subtle but important distinction

Neither Black nor Ruff is a substitute for a **type checker** or **test suite**.

For example:

```python
def add_numbers(a: int, b: int) -> int:

```

and then:

```python
result = add_numbers("hello", "world")
```

A formatter doesn't care.

Ruff may catch some related issues depending on the enabled rules, but it isn't fundamentally a type checker.

A type checker such as MyPy or Pyright is designed for that.

And only actually running your tests can tell you whether the program behaves correctly.

So think of the development pipeline as:

```text
                  Python code
                      │
        ┌─────────────┼─────────────┐
        ▼             ▼             ▼
      Ruff          Type          Tests
     lint/format    checker       pytest
        │             │             │
        └─────────────┼─────────────┘
                      ▼
                  good code
```

# 7. What does the Makefile do?

The Makefile is essentially a **command dispatcher / shortcut layer**.

Here's what the starter defines:

```makefile
setup: ; uv sync --frozen
seed:  ; python scripts/set_seed.py
ingest:; python scripts/run_ingest.py
index: ; python scripts/run_index.py
eval:  ; python scripts/run_eval.py
serve: ; uvicorn doc_agent.serve.api:app --host 0.0.0.0 --port 8000
lint:  ; ruff check . && black --check . && mypy src
test:  ; pytest
```

So, for example:

```bash
make ingest
```

is basically shorthand for:

```bash
python scripts/run_ingest.py
```

And:

```bash
make test
```

is shorthand for:

```bash
pytest
```

---

# 8. Why use a Makefile if the commands are so simple?

Because it gives the course a **standard interface**.

The instructor can say:

```bash
make setup
make seed
make ingest
make index
make eval
make test
make lint
```

and every team's repository should respond consistently.

Without Make, one team might use:

```bash
python thing.py
```

another:

```bash
./run_everything.sh
```

another:

```bash
uv run src/foo.py
```

The Makefile standardizes that interface.

It also makes shell scripts composable.

For example:

```bash
make ingest index
```

runs the two targets in sequence.

### File names


to:

```text

```

even if that seems cleaner.

---

### Module paths

Don't alter import locations expected by the grader.

---

### Function/class signatures

This is extremely important.

For example, the `Page` contract is:

```python
class Page(BaseModel):
    id: str
    image_path: str
    doc_id: str
```

You cannot decide:

```python
class Page(BaseModel):
    id: str
    image_path: str
    doc_id: str
    dpi: int
```

or rename fields.

The same applies to `Region`, `Chunk`, `Answer`, etc.

The tests explicitly check these structures.

---

### Pipeline order

This is locked:

```python
pages = loader.load_pages(cfg)
pages = preprocess.run(pages, cfg)
pages = enhance.run(pages, cfg)

regions = layout.detect(pages, cfg)

text = ocr.transcribe(regions, cfg)

chunks = chunk.split(text, cfg)

vectors = embed.encode(chunks, cfg)

store.build(chunks, vectors, cfg)
```

You cannot decide:

```text
OCR
→ layout
```

or:

```text
embed
→ chunk
```

because it makes more sense to you.


User: is there no command that pulls a branch into another one but automatically overwrites merges all conflicts in favor of one branch over the other?

Agent: Yes. Git has exactly this mechanism for a **merge where you want one side to win all conflicts**.

Suppose you're on `main` and want to merge `teammate-branch` into it, with the teammate branch winning conflicts:

```bash
git checkout main
git merge -X theirs teammate-branch
```

The important part is:

```bash
-X theirs
```

This tells Git:

> When the merge has a content conflict, prefer the version from the branch being merged in.

So:

```text
main
  + teammate-branch
        ↓
   conflicts → teammate version wins
```

### The opposite

If you're merging the teammate branch into `main` but want **your current `main` version** to win conflicts:

```bash
git merge -X ours teammate-branch
```

---

### Important distinction: `-X theirs` is not the same as `-s ours`

These are easy to confuse.

Use:

```bash
git merge -X theirs teammate-branch
```

when you want a **normal merge**, but want the incoming branch to win **content conflicts**.

Do **not** use:

```bash
git merge -s ours teammate-branch
```

unless you deliberately want Git to record the merge while essentially ignoring the incoming tree. That's a completely different operation.

---

### One caveat

`-X theirs` only resolves **actual merge conflicts** in favor of the incoming branch.

It does **not** mean:

> "Make every file in main identical to teammate-branch."

For example, if you have a file that exists only on your branch and the teammate branch doesn't touch it, that file can remain.

So for your situation:

#### Normal merge, teammate wins conflicts

```bash
git checkout main
git merge -X theirs teammate-branch
```

#### Make `main` exactly match teammate branch

```bash
git checkout main
git reset --hard teammate-branch
```

Given what you described earlier — your `main` has no meaningful commits and you want the teammates' architecture to completely replace yours — **`reset --hard` is the cleaner operation**.

If you specifically need a merge commit for your team's workflow/history, then:

```bash
git merge -X theirs teammate-branch
```

is the command you're looking for.

# 49. What happens when you run `make ingest`?

This is probably the most useful thing to understand.

You type:

```bash
make ingest
```

The Makefile executes:

```bash
python scripts/run_ingest.py
```

which does:

```python
pipeline.build_knowledge_base(config.load())
```

Then `pipeline.py` executes:

```text
1. wiring.register_all()
2. loader.load_pages()
3. preprocess.run()
4. enhance.run()
5. hooks.AFTER_INGEST
6. layout.detect()
7. ocr.transcribe()
8. hooks.AFTER_OCR
9. chunk.split()
10. hooks.BEFORE_INDEX
11. embed.encode()
12. store.build()
```

So the entire Stage 1–4 KB build is currently encapsulated in `build_knowledge_base()`.

That's why, despite the name, `make ingest` currently goes further than just loading pages.

# 7. What should the ground truth text look like?

# 13. How do you actually calculate the score?

Suppose you have:

```text
Gold:
"The solution is x² = 4."

Prediction:
"The solution is x2 = 4."
```

You normalize both according to your chosen normalization policy and calculate character-level precision, recall, and F1.

Conceptually:

```text
precision =
correct predicted characters
─────────────────────────────
all predicted characters

recall =
correct predicted characters
────────────────────────────
all gold characters

F1 =
2 × precision × recall
──────────────────────
precision + recall
```

Then calculate it across all held-out examples.

A simple macro-average would be:

```text
F1_page1
F1_page2
...
F1_page30

OCR-F1 =
(F1_1 + F1_2 + ... + F1_30) / 30
```

The exact implementation should be consistent across your notebook and later evaluation.

```text

```

versus:

```text

```

Likewise:

```text

```

versus:

```text
a b
```

could destroy mathematical meaning.

### Supporting

**Word error rate / word-level metric**

### Qualitative

# 15. But there is a major problem with naïve character F1

Suppose:

```text

\frac{-b \pm \sqrt{b^2-4ac}}{2a}

Prediction:
(-b ± √(b² - 4ac)) / 2a
```

These may be mathematically equivalent but look very different as strings.

A raw character metric could make the OCR look worse than it really is.

Therefore, for your project I would **not normalize away important mathematical errors**, but I would normalize harmless representation differences.

For example:

```text

```

might be removable.

Whitespace differences might be normalized.

But you should **not** normalize:

```text

```

or:

```text
\frac{a}{b} → a/b
```

without thinking carefully about whether the transformation changes the representation being evaluated.

```python
"""Governance — PII detection + redaction (mandatory)."""

from __future__ import annotations

import re

from ..contracts import *  # noqa: F401,F403


_EMAIL_RE = re.compile(
    r"\b[A-Za-z0-9._%+-]+@[A-Za-z0-9.-]+\.[A-Za-z]{2,}\b"
)

_SSN_RE = re.compile(r"(?<!\d)\d{3}-\d{2}-\d{4}(?!\d)")

# Conservative phone-number pattern. Requires separators so that ordinary
# mathematical numbers, years, page numbers, etc. are not treated as PII.
_PHONE_RE = re.compile(
    r"(?<!\d)"
    r"(?:\+?\d{1,3}[-.\s])?"
    r"(?:\(?\d{2,4}\)?[-.\s])"
    r"\d{3,4}[-.\s]\d{3,4}"
    r"(?!\d)"
)


def detect(text: str) -> list[tuple[int, int, str]]:
    """Return (start, end, type) spans for high-confidence PII."""
    spans: list[tuple[int, int, str]] = []

    for match in _EMAIL_RE.finditer(text):
        spans.append((match.start(), match.end(), "email"))

    for match in _SSN_RE.finditer(text):
        spans.append((match.start(), match.end(), "ssn"))

    for match in _PHONE_RE.finditer(text):
        spans.append((match.start(), match.end(), "phone"))

    # Keep deterministic ordering and remove overlaps.
    spans.sort(key=lambda item: (item[0], item[1], item[2]))

    result: list[tuple[int, int, str]] = []
    last_end = -1

    for start, end, pii_type in spans:
        if start >= last_end:
            result.append((start, end, pii_type))
            last_end = end

    return result


def redact(text: str) -> str:
    """Replace detected PII spans with explicit redaction markers."""
    spans = detect(text)

    if not spans:
        return text

    replacements = {
        "email": "[REDACTED_EMAIL]",
        "ssn": "[REDACTED_SSN]",
        "phone": "[REDACTED_PHONE]",
    }

    # Replace from right to left so original offsets remain valid.
    result = text

    for start, end, pii_type in reversed(spans):
        result = (
            result[:start]
            + replacements[pii_type]
            + result[end:]
        )

    return result


def register(hooks) -> None:
    """Wire PII redaction into the pipeline hooks."""

    def _scrub(ctx: dict) -> dict:
        if not isinstance(ctx, dict):
            return ctx

        # Common scalar text fields.
        for key in ("text", "answer", "log"):
            value = ctx.get(key)

            if isinstance(value, str):
                ctx[key] = redact(value)

            elif isinstance(value, list):
                ctx[key] = [
                    redact(item) if isinstance(item, str) else item
                    for item in value
                ]

        # OCR/chunk collections.
        chunks = ctx.get("chunks")

        if isinstance(chunks, list):
            for chunk in chunks:
                if isinstance(chunk, dict):
                    value = chunk.get("text")
                    if isinstance(value, str):
                        chunk["text"] = redact(value)

                elif hasattr(chunk, "text") and isinstance(chunk.text, str):
                    chunk.text = redact(chunk.text)

        hooks_context = ctx.get("context")
        if isinstance(hooks_context, str):
            ctx["context"] = redact(hooks_context)

        return ctx

    hooks.register(hooks.AFTER_OCR, _scrub)
    hooks.register(hooks.BEFORE_ANSWER, _scrub)
    hooks.register(hooks.ON_LOG, _scrub)
```

```python
"""Stage 4 — FAISS vector store."""

from __future__ import annotations

import json
from pathlib import Path
from typing import Any

import faiss
import numpy as np

from ..contracts import *  # noqa: F401,F403


def _paths(cfg: dict[str, Any]) -> tuple[Path, Path]:
    index_cfg = cfg.get("index", {})

    index_dir = Path(index_cfg.get("path", "data/index"))
    index_dir.mkdir(parents=True, exist_ok=True)

    return (
        index_dir / "index.faiss",
        index_dir / "chunks.json",
    )


def build(chunks, vectors, cfg: dict) -> None:
    """Build and persist the configured FAISS index plus chunk metadata."""
    index_cfg = cfg.get("index", {})
    index_type = str(index_cfg.get("type", "faiss:flat_ip"))

    if index_type != "faiss:flat_ip":
        raise ValueError(f"Unsupported index type: {index_type}")

    matrix = np.asarray(vectors, dtype=np.float32)

    if matrix.ndim != 2:
        raise ValueError(f"vectors must be 2-D, got shape {matrix.shape}")

    if len(chunks) != matrix.shape[0]:
        raise ValueError(
            f"chunk/vector count mismatch: "
            f"{len(chunks)} chunks vs {matrix.shape[0]} vectors"
        )

    if matrix.shape[0] == 0:
        raise ValueError("Cannot build an index from zero chunks")

    if not np.isfinite(matrix).all():
        raise ValueError("vectors contain non-finite values")

    # The embedding stage normalizes vectors. Inner product therefore
    # corresponds to cosine similarity.
    index = faiss.IndexFlatIP(matrix.shape[1])
    index.add(matrix)

    index_path, metadata_path = _paths(cfg)

    faiss.write_index(index, str(index_path))

    records = []
    for chunk in chunks:
        records.append(
            {
                "chunk_id": chunk.id,
                "doc_id": chunk.doc_id,
                "page_ids": list(chunk.page_ids),
                "text": chunk.text,
            }
        )

    metadata_path.write_text(
        json.dumps(records, ensure_ascii=False, indent=2),
        encoding="utf-8",
    )


def load(cfg: dict):
    """Load the persisted FAISS index and its chunk metadata."""
    index_path, metadata_path = _paths(cfg)

    if not index_path.exists():
        raise FileNotFoundError(f"FAISS index not found: {index_path}")

    if not metadata_path.exists():
        raise FileNotFoundError(f"Chunk metadata not found: {metadata_path}")

    index = faiss.read_index(str(index_path))

    records = json.loads(metadata_path.read_text(encoding="utf-8"))

    if not isinstance(records, list):
        raise ValueError("Chunk metadata must contain a JSON list")

    if index.ntotal != len(records):
        raise ValueError(
            f"Index/metadata mismatch: "
            f"{index.ntotal} vectors vs {len(records)} records"
        )

    return index, records
```
